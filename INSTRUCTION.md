# A1 Search Monitor — Инструкция эксплуатации (No-API, автономный запуск)

Документ для владельца сервиса, ответственного менеджера и администратора.

## 0. Цель

Поддерживать автоматическое, повторяемое измерение видимости объявлений A1 в выдаче Auto.ru и Avito на первых 3 страницах для каждого активного фильтра с разбивкой:

- факт показа (страница/позиция),
- подтверждённый непоказ,
- технический пробел (нельзя считать бизнес-фактом).

## 3. Семантика статусов (важно для принятия решений)

Внутри системы используется разделение:

- `FOUND_PAGE_1 / FOUND_PAGE_2 / FOUND_PAGE_3` — объявление найдено на странице;
- `ABSENT_CONFIRMED` — не найдено на страницах 1–3 после валидной проверки;
- `ABSENT_UNCERTAIN` — возможный непоказ с сомнительным техническим контуром;
- `TECHNICAL_ERROR` / `UNKNOWN_TECHNICAL` — отказ инфраструктуры или парсинга.

`ABSENT_CONFIRMED` имеет управленческую ценность только при успешном техническом выполнении цикла и полного сканирования 1–3 страниц.

## 4. Эпизоды отсутствия

- Эпизод открывается после 2 подтверждённых подряд `ABSENT_CONFIRMED`;
- закрывается первым последующим `FOUND_*`;
- технические ошибки не закрывают эпизод и не продлевают его автоматически;
- отчёт по эпизодам берётся из `GET /api/v1/dashboard/missing`.

## 5. Жизнь при изменении структуры таблицы подрядчика

Система корректно обрабатывает:
- перестановку колонок;
- добавление служебных/вспомогательных колонок;
- алиасы заголовков, описанные в `docs/DATA_CONTRACT.md`.

При критичном дрейфе:
- создаётся `SourceImportSnapshot` со статусом `blocked_by_schema_drift`;
- активный реестр объявлений не меняется автоматически;
- запуск сканирования продолжается по последней валидной версии;
- инцидент отправляется в журнал тех.событий.

## 6. Выходные дни

Мониторинг работает ежедневно (7/7).

В понедельник выполняется проверка:
- не завершённые и начатые в выходные эпизоды;
- количество технических пробелов в выходные;
- сравнение с понедельничной «нормальной» метрикой по каждому фильтру.

## 7. Обратная связь менеджеров

Механизм:
`POST /api/v1/feedback`

Поля:
- `listing_id`, `filter_id`, `severity`, `category`, `message`, `manager_name`, `source`.

Статусы тикета:
`new -> checking -> assigned -> fixed -> confirmed`.

Изменение статуса тикета **не меняет** факт наблюдения автоматически.

## 8. Инциденты и действия

Срабатывать при:
- массовых `TECHNICAL_ERROR`;
- резком росте `UNKNOWN_TECHNICAL`;
- массовом нулевом покрытии одной платформы;
- пропуске расписания сканирования.

Действия:
1. Зафиксировать инцидент (время, платформа, фильтры, версия).
2. Проверить диапазон (`всё / один источник / отдельные фильтры`).
3. Оценить технический шум vs бизнес-показ.
4. Сделать точечный фикс адаптера без изменений смысловой логики.
5. Выполнить контрольный прогон и только потом возвращать штатный режим KPI.

## 9. Безопасность и эксплуатация

- `.env` не хранится в репозитории.
- Не логировать токены/идентификаторы сессии.
- Периодически делать backup БД и проверить restore на тесте.
- Ограничить доступ к API (`network policy`, basic auth/ reverse proxy).
