# A1 Search Monitor — BIBLE v1.2

Утверждённые правила системы. Изменения возможны только по решению Owner с фиксацией причины в журнале изменений.

**Дата актуальности:** 4 сентября 2026  
**Часовой пояс:** `Europe/Moscow`  
**Цель:** устойчивый облачный мониторинг видимости объявлений без API платформ и без зависимости от локального ПК.

## 1. Неизменяемые принципы (без компромиссов)

1. **Никаких API Auto.ru/Avito.**  
   Все данные выдачи получаем только через публичные страницы и рендеринг браузера (Playwright).

2. **Cloud-first запуск.**  
   Нельзя считать задачу выполненной, если мониторинг завязан на локальный компьютер.

3. **Три страницы как единая единица анализа.**  
   Проверка по умолчанию = страницы 1, 2, 3 (по каждому активному фильтру и источнику).

4. **Технический результат не равен факту непоказа.**  
   Состояния `TECHNICAL_ERROR` и `UNKNOWN_TECHNICAL` не создают управленческий факт отсутствия.

5. **Импорт устойчив к дрейфу, но не рискует потерять рабочую референсную историю.**  
   Критичный дрейф структуры входной таблицы переводит импорт в карантин и не перезаписывает активный реестр до ручного подтверждения.

6. **Append-only наблюдения.**  
   Исторические наблюдения и эпизоды закрытия никогда не удаляются и не затираются.

7. **Выходные обязательны к учёту.**  
   Система работает 7/7, и отчёт по пропускам на выходных обязателен в плановую выдачу.

8. **Нет автоматических управленческих действий по непроверенным данным.**  
   Автоматическое закрытие/пропуск рекламных решений на основе невалидного технического статуса запрещено.

## 2. Источники истины

1. **PostgreSQL** — state-1 for listings, filters, observations, absence_episodes, feedback, import snapshots.
2. **SourceImportSnapshot** — точка контроля изменений источника от подрядчика.
3. **ListingObservation** — каждый фактический результат конкретного прогона.
4. **AbsenceEpisode** — длительные интервалы отсутствия по объявлению + фильтру.
5. **ManagerFeedback** — отдельный канал качества, не влияющий автоматически на факт статуса.

## 3. Схема статусов

- `FOUND_PAGE_1`, `FOUND_PAGE_2`, `FOUND_PAGE_3` — факт показа.
- `ABSENT_CONFIRMED` — не найдено в полном валидном проходе (1–3 страницы).
- `ABSENT_UNCERTAIN` — не найдено, но с техническими оговорками.
- `FILTER_MISMATCH` — найдено, но не соответствует критериям связи (при расширении).
- `TECHNICAL_ERROR` / `UNKNOWN_TECHNICAL` — инфраструктурная/парсерная проблема.

**Условия `ABSENT_CONFIRMED`:**
1. все запланированные страницы отсканированы успешно;  
2. парсинг карточек стабильный и детерминируемый;  
3. пара (listing, filter, source) имела активную Expectation;  
4. нет валидного `FOUND_*` в текущем цикле для этой пары.

## 4. Логика эпизодов

1. Открытие эпизода — после двух последовательных `ABSENT_CONFIRMED`.
2. Начало эпизода — timestamp первого из двух подтверждений.
3. Закрытие — первое последующее `FOUND_*`.
4. `TECHNICAL_ERROR`/`UNKNOWN_TECHNICAL` в серии **не закрывают** эпизод и не повышают подтверждение.

## 5. Контроль качества импорта

Допустимо:
- изменение порядка колонок;
- добавление неиспользуемых колонок;
- синонимы/алиасы полей (список в `docs/DATA_CONTRACT.md`).

Критичный дрейф:
- ключевые поля для сигнатуры объявления отсутствуют;
- конфликтующие обязательные маппинги;
- критически высокий уровень неизвестных обязательных заголовков.

Реакция:
- `blocked_by_schema_drift = true` у snapshot;
- `active` реестр не меняется;
- issue для Owner с указанием первопричины.

## 6. Критерии качества релиза

- 5+ дней пилота в рабочих условиях;
- ≥14 дней стабильной работы для v1.0 (по согласованию может быть сокращено с допуском управления рисками);
- отсутствие валидационных ложных `ABSENT_CONFIRMED`;
- покрытие smoke и базовых сценариев;
- документированные runbooks и run cadence.

## 7. Наблюдаемые метрики

- `coverage_run_pages` (сколько страниц отсканировано по платформам/фильтрам);
- `found vs missed` по фильтрам и источникам;
- доля технического шума;
- `absence_open_duration` (возраст открытых эпизодов);
- freshness of latest successful import;
- число новых тикетов менеджеров и доля закрытых.

## 8. Запреты

- не менять смысл `ABSENCE` при недоступности сети к площадке;
- не использовать несанкционированные обходные методы для API;
- не удалять исторические наблюдения, чтобы не искажать ретроспективу.
