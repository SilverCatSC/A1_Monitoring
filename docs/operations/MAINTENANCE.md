# Поддержка и учёт изменений

## Перед изменением

1. Открыть [BIBLE](../../BIBLE.md), [структуру](../architecture/PROJECT_STRUCTURE.md)
   и [актуальный аудит](../analysis/AUDIT_2026-09-14.md).
2. Проверить `git status --short`. Не удалять незакоммиченные файлы других работ.
3. Зафиксировать воспроизводимый дефект, ожидаемый результат и пример без секретов.
4. Отдельно согласовать live-обход, публикацию или платный API, если они нужны.

## Резервирование

Папка `Monitoring` и PostgreSQL — два разных хранилища. БД и автоматические
дампы находятся в Docker volumes. Не использовать `docker compose down -v`:
это может удалить историю.

На Mac существующие команды:

```bash
./scripts/backup_now.sh
./scripts/restore_test.sh
```

Первая пишет дамп в backup-volume. Вторая восстанавливает его во временную БД,
проверяет SHA-256 и структуру dump, сравнивает revision Alembic и количества
`listings`, `source_import_snapshots`, `monitoring_cycles`, `manager_feedback`,
затем удаляет только эту временную БД. Проверка не охватывает все связи, снимки
и AI-артефакты.
Запускать после свежего backup без параллельного импорта, иначе сравнение
количеств с меняющейся основной БД может дать ложную ошибку.

На Windows те же защищённые DB-операции:

```powershell
.\scripts\backup_now.ps1
.\scripts\restore_test.ps1
```

Они работают только через Docker Compose, оставляют DB-dump внутри backup-volume
и удаляют лишь сгенерированную временную БД. PowerShell-скрипты проверены
статически, но не выполнялись на MSI/Docker Desktop; до этого не считать их
приёмкой Windows.

Для полного переноса на Windows требуется отдельно:

1. Дамп PostgreSQL и копия `artifacts/evidence`, реестровых/AI-отчётов.
2. Защищённая копия настроек `.env`; версии lock-файлов и commit/снимок исходников.
3. Восстановление в отдельный новый экземпляр PostgreSQL, не поверх единственной
   рабочей базы.
4. Проверка количества автомобилей, наблюдений, сверок, замечаний, импортов,
   а также открытия старых снимков из интерфейса.
5. Исправление абсолютных Mac-путей в индексах артефактов отдельной миграцией.
6. Только после приёмки переключение основного компьютера.

Restore-скрипт проверяет только PostgreSQL. Не выдавать обычное копирование
каталога за полный перенос БД+доказательств на другой компьютер.

## Безопасность

Не коммитить `.env`, cookies, браузерные профили, дампы, приватные JSON/CSV,
агентские HOME и модели. Перед push проверить игнорирование и staged diff.
Публичный код допустим; внутренний отчёт отдела продаж должен иметь отдельную
политику доступа. Public export теперь создаёт только отдельную агрегированную
страницу и требует свежий owner allowlist; это не разрешает публиковать прежние
внутренние HTML-страницы.

AI-провайдеру можно передавать только согласованный минимум. Текст объявления
считать недоверенными данными: он не должен менять системные инструкции агента,
включать инструменты или разрешать публикацию/изменение кода.

## Регулярный контроль

Ежедневно: свежесть импорта/поиска/прямых карточек, CAPTCHA, незавершённые этапы.
Еженедельно: спорные совпадения без VIN, перевыкладки, feedback, выборочная ручная
проверка, backup. Перед изменением структуры таблицы: контракт колонок и preview
импорта. Перед сменой модели: фиксированная выборка эталонов, стоимость и качество.

Ответственный оператор управляет запусками; маркетинг исправляет источники;
менеджер подтверждает ошибки; разработчик меняет код. LLM не заменяет владельца
данных и не получает автоматическое право менять production.
