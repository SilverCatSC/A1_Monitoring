# Архитектура 0.9

Реализованный контур: macOS + видимый Chrome. Web и PostgreSQL работают в Docker.
Облачная версия из deploy/cloud — прежняя заготовка, не текущий способ мониторинга.

Основная рабочая машина по последнему решению владельца — MSI с Windows 11 и
16 ГБ RAM; macOS сохранён как дополнительный контур. Целевой публичный
код: SilverCatSC/A1_Monitoring; отдельный статический отчёт готовится для GitHub
Pages со ссылкой из Битрикс. Публикация и отправка ссылки остаются отдельными
явными действиями владельца.

## Границы компонентов

1. Локальный worker читает Google Sheets CSV, проверяет снимок и обновляет реестр.
2. FilterRegistryService назначает автомобили утверждённым поисковым сценариям.
3. SellerReconciliationService сверяет ссылки со свежими каталогами продавца через
   видимый Chrome. Похожие объявления — кандидаты, не автоматическая замена.
4. Адаптер площадки читает поисковые страницы, сохраняет доказательства.
5. MonitorService проверяет видимость только подтверждённых текущим этапом ссылок,
   записывает наблюдения и эпизоды. Неясная связь даёт technical_error, не непоказ.
6. После поиска SellerReconciliationService последовательно открывает текущие
   прямые карточки, извлекает ограниченный набор полей и сохраняет viewport-снимок.
   CAPTCHA останавливает последующие обращения к площадке.
7. HeadTableAudit детерминированно сопоставляет прямые карточки с ценой, VIN, годом,
   статусом/наличием и НДС головной таблицы.
8. Analytics/report строят read-only представления; Web не запускает скрытый обход.
9. Hermes анализирует малые задания по одному автомобилю на лёгкой локальной
   модели; тяжёлый профиль выборочно аудирует спорные результаты по явному запросу.
10. FeedbackService ведёт обсуждение и подтверждение исправлений.

## Основные сущности

| Сущность | Что означает |
| --- | --- |
| Listing | Автомобиль реестра, преимущественно идентифицируемый VIN |
| Размещение (проекция) | Listing × площадка × canonical marketplace ID |
| SearchFilter | Утверждённые URL/критерии с версией |
| VehicleFilterExpectation | Ожидание автомобиля в конкретном фильтре |
| ScanRun | Обход одной площадки, профиль сети и технический результат |
| ListingObservation | Факт проверки автомобиля в одном фильтре |
| ListingChangeEvent | Изменения полей реестра с old/new и snapshot_id |
| ListingLinkEvent | История прямых ссылок, включая ручное подтверждение |
| ListingLinkOverride | Подтверждённая локальная ссылка и последнее значение из таблицы |
| ListingReconciliation | Неизменяемый результат сверки связи, кандидаты и batch_id |
| DealerDiscoveryRun / DealerListingCandidate | Результат обхода каталога и найденные публикации |
| AbsenceEpisode | Серия валидных непоказов; ошибка сети не является непоказом |
| SourceImportSnapshot | Итог прочтения источника и решение о карантине |
| ManagerFeedback / FeedbackEvent | Замечание и история его обработки |

С 0.7 наблюдение хранит expected_listing_key, expected_listing_url, filter_version,
filter_url и app_version в raw_payload. Прошлые наблюдения не переписываются.
Старые непоказы без ID нельзя надёжно отнести к переопубликованному объявлению.

С 0.8 наблюдение также ссылается на конкретную предварительную сверку. Один lock
защищает весь цикл импорт → каталоги → поиск и ручное подтверждение ссылки.
Кандидат из прошлого обхода не считается свежей проверкой. Подтверждённые связи
не перезаписываются импортом; конфликт с таблицей виден на экране сверки.

С 0.9 `ListingReconciliation.details.direct_inspection` хранит состояние прямой
карточки, причину, снимок и извлечённые поля. Это не поисковое наблюдение и не
утверждение о фактической продаже автомобиля компании. Одностраничная sales-
проекция объединяет активный Monitoring с несопоставленными активными строками
последнего локального снимка головной таблицы.

Замена ссылки не означает продажу автомобиля. Деактивация в реестре не является
доказательством снятия объявления на площадке. Время импорта не равно времени
редактирования подрядчиком или публикации площадкой.

## Поддержка

Продуктовые правила — BIBLE.md. Определения вычислений — METRICS.md. Схема
меняется через Alembic, а не ручной правкой production SQL. Новый frontend framework
не добавляется: серверные страницы и небольшой JavaScript достаточны текущему объёму.
При росте истории аналитические агрегации следует перенести в SQL/материализованные
представления: сейчас выбранный период до 90 дней агрегируется в памяти приложения.
